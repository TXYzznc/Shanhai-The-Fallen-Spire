## Context

仓库当前处于一次未提交的大规模迁移中：旧资产和旧配置大量删除，新的 GF_X、agent、SKILL、OpenSpec 与工具目录尚未纳入 Git。运行时代码目录已基本没有可识别的具体玩法代码，但业务语义仍广泛存在于治理文件、领域型 SKILL、agent prompt、OpenSpec 主规格、playtest 证据、热更 DLL、HybridCLR 生成物和资源说明中。

本次目标不是制作“通用游戏示例工程”，而是建立一个不携带任何玩法领域知识、业务实例或样例资产的框架基线。后续示例由用户在此基线上另行添加。

约束：

- 不直接修改 `.codex/agents/*.toml`；只修改 `.claude/agents/*.md` 后运行同步脚本。
- `Assets/Game/ScriptsBuiltin/` 是 GF_X 框架核心，除非有明确业务耦合证据，否则只审计不重写。
- 保留 Unity 2022.3.62f3 可用的框架与必要依赖。
- 不回滚当前工作区的既有迁移改动。
- 当前未跟踪文件没有 Git 恢复点，执行删除前必须生成精确清单并完成引用审计。

## Goals / Non-Goals

**Goals:**

- 当前工作树中不再存在具体项目、玩法、角色、关卡、战斗、经济、任务、成就、引导等领域制品或样例。
- 仅保留领域无关的 Unity/GF_X 框架、工程自动化、构建、诊断、测试基础设施和元工作流。
- 所有保留的 agent、SKILL 与文档不得硬编码项目名、业务目录、业务数据文件或业务生命周期。
- 清除业务编译产物和陈旧生成物，确保后续项目从空业务状态重新生成。
- 提供可重复运行的框架纯度审计，防止残留回流。

**Non-Goals:**

- 不创建启动场景、演示场景、示例 Prefab、示例配置或测试样例。
- 不为被删除的业务能力提供占位实现。
- 不重新设计 GF_X 框架核心。
- 不升级 Unity、GF_X 或第三方包版本。
- 不提交、推送或重排用户当前 Git 历史。

## Decisions

### 1. 采用严格允许清单，而不是关键词删除

候选方案：

1. **严格允许清单**：仅保留已证明属于框架或工程工作流的目录与能力。
2. 关键词拒绝清单：搜索已确认的历史产品标识、业务类型名和业务资源路径后逐项删除。
3. 全部迁入仓内历史归档：把不确定内容移动到新的归档目录。

选择方案 1。关键词拒绝清单容易遗漏改名后的业务耦合，也会误伤 Unity API 中的 `Player` 等合法平台术语；历史归档仍会污染搜索、索引和 AI 上下文。允许清单配合引用审计最符合“纯框架”目标。

允许内容分为：

- GF_X 框架核心及其编辑器工具；
- Unity 2022.3.62f3 所需项目设置和第三方依赖；
- 与玩法领域无关的构建、诊断、资源处理、序列化、输入抽象、异步、测试和发布基础设施；
- 需求澄清、OpenSpec、代码审查、风险管理、文档生成等元工作流。

### 2. 领域型 SKILL 直接删除，不进入候选淘汰区

成就、战斗平衡、赌场数学、难度曲线、玩法经济、关卡、玩家引导/引入、成长、谜题、任务、GDD 传播等 SKILL 属于业务设计知识，不属于框架能力，必须从 `.claude/skills/`、索引、矩阵、agent 白名单和 Codex 镜像中同时移除。

保留的工程型 SKILL 若含具体项目名、固定业务路径或玩法案例，必须删去这些内容或改写成参数化约束。若删去后没有独立工程价值，则删除整个 SKILL。

### 3. 业务历史从当前树删除，不建立仓内归档

业务 OpenSpec 主规格与 archive、playtest 报告、截图、测试结果和旧说明不迁入其它仓内目录。已跟踪内容由 Git 历史恢复；未跟踪内容在删除前记录路径、哈希和分类，但不复制其正文或资源到仓库。

本次 OpenSpec change 自身只记录清理规则与执行结果，不复制被清理的业务内容。

### 4. 生成物按“可再生且无业务输入”原则处理

`Assets/Game/HotfixDlls`、`Assets/HybridCLRData` 等包含业务类型或来自旧业务程序集的输出必须删除。对应生成管线和配置若属于框架则保留，并验证在空业务输入下不会引用已删除类型。

字体、材质、Shader、语言文件和 ScriptableObject 资产不因“看起来通用”自动保留；只有被框架启动或编辑器工具直接引用、且没有业务数据的最小资产可以保留。

### 5. 验收分为静态纯度、引用完整性和编译健康三层

- 静态纯度：允许清单、禁用路径/标识、业务制品清零。
- 引用完整性：Unity GUID、asmdef、脚本、配置、agent↔SKILL、OpenSpec 索引无悬空引用。
- 编译健康：Unity batchmode 或已连接 Editor 完成重新导入和编译；GF_X 全量诊断中不依赖业务场景的项目通过。

没有场景和业务数据是预期结果，不以“可进入 Play Mode”作为本次验收条件。

## Risks / Trade-offs

- [领域型 SKILL 删除后能力覆盖下降] → 后续项目按实际类型安装或新增项目级 SKILL，不把可选业务知识塞回框架核心。
- [关键词审计误报 Unity API 的 Player/RuntimePlatform] → 关键词只用于发现，最终依据路径、上下文和允许清单判定。
- [未跟踪业务文件删除后不可由 Git 恢复] → 删除前输出带哈希的清理清单，由用户可见确认过的严格规则约束目标。
- [删除生成物导致首次打开工程重新导入时间增加] → 保留生成脚本与包配置，接受一次性重生成成本。
- [无场景导致部分 GF_X 诊断不可运行] → 将“需要业务/场景”的诊断标记为不适用，保留纯编辑器与静态诊断。
- [当前工作区非常脏，难以用 git diff 区分本轮变更] → 全程按精确路径分批操作，并为每批记录删除/修改清单。

## Migration Plan

1. 生成仓库分类清单：框架核心、工程工作流、领域业务、样例/历史、生成物、待人工判定。
2. 清理治理层：agent、SKILL、索引、矩阵、hooks、说明文档中的业务耦合。
3. 清理 OpenSpec 主规格和归档，仅保留框架与工程治理能力。
4. 清理 playtest、截图、测试结果、业务工具和旧业务说明。
5. 清理 Unity 业务资产、热更 DLL、HybridCLR 业务生成物及悬空配置。
6. 从 `.claude/agents/` 重新生成 `.codex/agents/`。
7. 运行静态纯度、引用、OpenSpec、Python 工具测试和 Unity 编译/诊断验证。
8. 将最终审计结果写入本 change 的测试结果，不新增样例。

回滚依赖 Git 中已跟踪内容；对未跟踪内容，本变更只删除被规则明确判定为业务制品的目标。
