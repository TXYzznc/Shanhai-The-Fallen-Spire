## Context

目标框架已有 agent、SKILL 与 OpenSpec 的基础治理，但没有将多窗口协作的事实来源、占用管理和交接规则固化为可初始化、可验证的框架能力。来源项目的机制已被实际使用，但其文档含有产品名、活动派发、任务编号、端口和绝对路径，不能直接迁入基线。

## Goals / Non-Goals

**Goals:**

- 以 `Documentation/Development/Dispatch/` 提供默认协作规范、空模板和新项目初始化说明。
- 以 `ActiveAssignments.md` 作为制作人独占的持久协作总览，以 `.ai/dispatch/window-registry.local.json` 保存本机窗口标识。
- 在入口、OpenSpec spec 和审计脚本中统一可验证的协作契约。

**Non-Goals:**

- 不创建窗口、不登记真实占用、不自动更改外部权威计划或用户验收结论。
- 不迁移产品 OpenSpec、业务代码、资产、任务状态、端口或路径。
- 不改变 `.claude/agents` 的来源机制或直接编辑 `.codex/agents`。

## Decisions

### 文档为持久协作事实来源

派发单、中央占用、OpenSpec、提交和验收证据是持久事实来源；跨窗口消息仅传递最小启动或制作人动作请求。这样消息失效时可安全降级到手动派发。

### 分层路由

长期用户可见工作窗口按职能声明优先 agent/技能方向，但可使用当前环境能力完成必要检查。只有显式委派的子 agent 受 `.claude/SKILL_MATRIX.md` 和对应配置的白名单约束，避免把窗口上下文误当成 agent 权限扩张。

### 参数化与本机状态隔离

所有项目名、路径、窗口标题、工具实例、端口和权威计划源由初始化时填入。真实注册表只放在 `.ai/dispatch/` 并由 Git 忽略；基线只提交结构示例与空模板。

### 轻量静态审计

扩展既有纯度审计，在受管入口和 Dispatch 文档中检查必需制品、禁止的产品标识及 `.gitignore` 规则，并以 Python 单元测试锁定规则。审计不解析或保存本机注册表内容。

## Risks / Trade-offs

- [文档规则可能与产品流程不完全吻合] → 明确项目可在项目层扩展，框架只规定最小契约。
- [集中占用表成为写冲突点] → 仅制作人窗口写入，其他窗口通过回传请求更新。
- [端口或项目名误配] → 使用占位符，要求派发前核对目标项目和工具锁。

## Migration Plan

1. 添加 OpenSpec、规范、模板、初始化说明和入口链接。
2. 更新审计及测试并运行同步/纯度/OpenSpec 验证。
3. 新项目复制框架后执行初始化说明创建本机注册表与第一份空派发；已有项目可逐步采用，不需要迁移历史派发。

## Open Questions

无；批次格式、默认能力、审计范围和分层路由已由制作人确认。
