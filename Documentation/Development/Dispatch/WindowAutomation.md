# 固定窗口注册与自动派发

窗口消息是派发单的传输与状态监控层；派发单、OpenSpec、提交、验收证据和项目权威计划仍是正式事实来源。

## 首次注册与派发

1. 用户创建长期职能窗口，或明确要求制作人创建指定窗口。
2. 项目为窗口设置稳定标题和项目绑定；制作人将实际 `threadId`、`hostId` 和项目标识写入本机注册表。
3. 制作人写入派发单、登记批次边界并核对无冲突后，向已注册窗口发送最小启动消息。
4. 注册无效、窗口不匹配或发送失败时，记录原因并降级为用户手动派发；不得路由到看似相近的项目窗口。

真实注册表为 `.ai/dispatch/window-registry.local.json`，必须被 Git 忽略。仅在标题、职能和项目绑定都匹配时自动重绑；任何歧义交由用户确认。

## 最小启动消息

```text
你是 <project-name> 的 <role-window>。请处理派发 <dispatch-id>。
先阅读 <dispatch-document> 并完成启动检查。正式事实以派发单、OpenSpec 与项目文档为准。
在派发边界内自主推进，用户决定直接记录并点对点同步相关窗口；每两轮讨论自行增量归档。
提交时向 <git-integration-window> 发送精确请求。只有范围/依赖变化、未解决冲突、新授权、共享资源异常、S0/S1 或整个批次完成时才联系制作人。
```

发送前制作人必须确认派发已登记、目标窗口有效且绑定正确、目录/高冲突文件没有未交接冲突，并在需要驱动工具时定位当前使用窗口。

## 回传门槛

专业窗口从本机注册表读取 `producer`、`git-integration` 和相关协作窗口。提交请求发给 Git 集成窗口；职责内用户决定直接通知受影响窗口。仅在以下情况联系制作人：

- 范围、优先级、负责人、排期、OpenSpec 编号/边界/依赖需要变化；
- 点对点沟通后仍无法消除的设计、文件、交付或验收冲突；
- 工具实例失联占用、目标项目异常、破坏性操作风险或新增写权限；
- Git 集成窗口发现路径归属不明、只读文件混入或仓库异常；
- 发生 S0～S1 暂停事件，或整个派发批次完成。

普通讨论检查点、单项用户决定、测试通过、两轮增量归档、独立提交和无需制作人动作的完成不得广播。制作人请求至少包括派发 ID、事件类型、需要采取的动作、验证结果和当前占用资源。制作人可在协调回合等待必要回传；低频巡检仅作兜底，不能替代主动回传。

## 自动化边界

- 未经用户明确要求，不创建新的用户可见窗口。
- 自动化不代替用户的方案、验收或权限扩张决定，也不得自动改写权威计划。
- 同一工具实例同一时段只允许一个窗口驱动；派发前确认目标项目和实例身份。
